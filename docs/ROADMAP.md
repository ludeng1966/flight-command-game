# 项目路线：多单位实时战术指挥

> 状态：方向与计划文档。短期计划截至“换引擎前”。文中区分**现有能力**与**计划能力**，未接入的功能不得在实现或界面中写成已实现。
>
> 相关文档：[README](../README.md) · [AI 开发说明](../AGENTS.md) · [协作流程](team-collaboration.md) · [指挥游戏说明](../game/README.md) · [服务与 AI](../server/README.md)

## 1. 一句话定位

做一个军事指挥类 RTS：**先把基本玩法做好，之后把代码移植到 Godot，用 Godot 继续开发更好的交互、玩法与 PVE 关卡。**

核心不是让玩家操纵单机，而是让玩家坐在指挥部里做两件事：**态势研判**和**兵力调度**。玩家决定谁去哪里、守哪一侧、什么时候增援或撤回；具体飞行由程序飞行员完成。

仓库内的 WTACRP 回放查看器仅作代码参考，不纳入本路线。

## 2. 为什么是自然语言，为什么是持续意图

方向原文（聊天记录）：

> 我想提议把它做成以态势研判和兵力调度为核心的多单位实时战术指挥游戏。玩家坐在指挥部里，决定谁去哪里、守哪一侧、什么时候增援或撤回，具体飞行由程序飞行员完成。
>
> 我之所以倾向这个方向，是因为自然语言天然有操作成本。一句话要组织、说出、理解。如果滑行、起飞、转弯都要逐项开口，玩家很容易觉得，与其这样指挥一架飞机，还不如去玩《王牌空战》或《战争雷霆》自己开。语音更适合表达有持续作用的意图，比如 Bravo 守住东侧，别追出防区，下达这条命令后，Bravo 会继续执行，玩家就能把注意力转向 Alpha 和整个战场。

由此得到的设计约束：

- 单条指令应表达**持续意图**（守住某区、禁止追击、增援、撤回、条件触发），程序飞行员负责把意图变成连续飞行；
- 不把逐项操纵（滑行、起飞、转弯、油门）当成核心交互；这些可以作为教学或高级控制存在，但不构成主要玩法；
- 语音/文字只是输入方式之一，核心是**指挥意图的表达与执行**，不是语音识别本身；
- 玩家注意力应留给态势判断和兵力分配，而不是盯住单机仪表。

## 3. 核心体验：有限兵力下的取舍

方向原文（聊天记录）：

> 核心的爽点在于有限兵力带来的取舍，而且下令的时机会改变结果。比如 Alpha 在北侧请求增援，Bravo 是东侧唯一的守军。现在调 Bravo，北侧更有把握，但东侧会出现空窗；再等一会儿，东侧多守了一阵，北侧却可能错过机会。玩家可以根据情报押一个判断，也能在发现自己判断错了以后停止追击、重新布防，争取翻盘。这种靠玩家决策操作赢得局面的方式我认为是我们最大的卖点之一。

落地时必须具备的要素：

1. **有限兵力**：单位数量不足以同时覆盖所有方向，防区之间存在真实空窗；
2. **时机压力**：同一决策早做和晚做结果不同，存在窗口期与机会成本；
3. **情报与不确定性**：玩家基于不完整信息判断，允许押错；
4. **可恢复性**：发现判断错误后，能停止追击、重新布防，通过后续决策翻盘；
5. **胜负来自决策**：胜负主要由态势判断和兵力调度决定，而不是操作速度或单机狗斗技术。

## 4. 总路线

### 阶段 0：当前原型（Web + Node）

已具备的验证基础：

- 两架 F-16A Block 10、完整飞行物理、程序飞行员、航路规划与安全试飞；
- 自然语言/语音指挥链路：玩家原话 → 指挥官模型 → 程序校验 → 飞行员规划 → 原子装订 → 结果检查复述；
- 机场运行、雷达、导弹、RWR、教学与存档；
- 严格 JSON Schema、能力表诚实声明、模拟上游回归。

本阶段要回答的问题：**“态势研判 + 兵力调度 + 持续意图”是否已经构成可玩的循环？** 现有原型主要验证了单/双机指挥与飞行执行，还没有多单位战场、防区与时限压力。

### 阶段 1：换引擎前（当前重点）

目标：在现有原型上把**基本玩法闭环**做出来，并把可移植部分与表现层解耦。

- 多单位（大于当前两机）在同一场景中接受调度；
- 持续意图与防区/禁令/条件触发；
- 情报不确定性、增援与撤回、时限与胜负；
- 至少一个可重复游玩的 PVE 场景；
- 命令协议、世界状态与事件结构稳定到可以移植；
- 回归测试覆盖核心循环。

### 阶段 2：Godot 移植

原则：先搬“规则与仿真”，再重做“表现与输入”。

- 移植 `sim/` 的任务、飞控、物理、机场、传感器、武器与命令协议；
- 重做渲染、镜头、输入、UI 与语音交互；
- 用阶段 1 的验收场景和回归用例对齐行为；
- 保留“模型提议、程序裁定”的边界，不把裁定逻辑搬进表现层。

### 阶段 3：Godot 上继续开发

- 更好的指挥交互（态势图、编组、任务卡、时间轴、撤销/重做）；
- 更丰富的玩法（多机种、地面目标、防空威胁、电子战等，按优先级逐步接入）；
- PVE 关卡与战役；
- 任务/场景编辑器与内容生产流程；
- 性能、存档、回放与（如需要）多人。

### 换引擎的判定标准

满足以下条件后再切换主开发引擎：

1. 核心循环在现有原型上可玩、可重复，并有人愿意反复玩；
2. 仿真与命令协议不依赖浏览器或 Node 特有 API，边界清晰；
3. 世界状态、命令协议、事件与存档格式有版本号和兼容策略；
4. 核心循环有自动化回归，Godot 侧可用同一组用例验收；
5. 已列出移植清单：哪些直接搬、哪些重写、哪些放弃。

## 5. 短期计划（截至换引擎前）

### 5.1 玩法与指挥体验（负责人待定，项目负责人牵头）

- 多单位选择、编组与任务分配；
- 防区/警戒区/禁飞区/追击限制等持续意图；
- 增援、撤回、换防、条件触发（例如“接触敌机后撤回”“东侧失守则增援”）；
- 态势图：接触、情报可信度、单位状态、剩余兵力、时间压力；
- 胜负条件与评分：任务目标、损失、时间、平民/设施等（按场景定义）；
- 至少一个 PVE 场景，用于验证“有限兵力 + 时机取舍”。

验收：玩家能在不逐项操纵的情况下，用若干条持续意图完成一次调度；同一场景存在至少两种合理解法，且早做/晚做结果不同。

### 5.2 物理仿真：天气、能见度、机场助降（奕奕奕奕然）

现有基础：

- `sim/airport-weather.js`：风、阵风、风切变、能见度、云底、QNH、温度、跑道状况与 ATIS；
- `sim/airport-procedures.js`：目视/ILS/RNAV/起落航线进近、下滑道与航向道偏差、最低能见度与云底；
- 天气已影响风、密度、指示高度和进近限制。

本阶段目标：

- **天气系统**：从单点静态参数扩展到随场景/时间变化；明确对飞行、雷达、武器和机场运行的影响；保留可复现的随机种子；
- **能见度**：雾、云底、降水、RVR 等对目视发现、进近最低标准和 AI 判断的影响；
- **机场助降系统**：完善 ILS 航向台/下滑台信号、DME、进近灯与复飞逻辑；补齐信号失效、降级运行和与能见度的耦合；
- 为指挥层提供可读的天气/跑道状态，而不是只做视觉表现。

验收：同一场景在不同天气/能见度下产生可解释的战术差异；助降信号失效时能正确降级或复飞；参数与影响写入文档和测试。

### 5.3 雷达、导航、机场调度与空域（xy小宇）

现有基础：

- `sim/radar.js`：PD/脉冲、杂波、地形遮蔽、视距与万向节限制；
- 航路、靶眼与导航几何；TACAN 目前只教几何，尚无实际调谐接收机；
- `sim/airport*.js`：滑行、跑道外等待、对正、起飞、进近、着陆、复飞与地面调度。

本阶段目标：

- **雷达系统**：完善搜索/跟踪、探测概率与情报输出，明确“传感器看到什么”和“指挥层知道什么”的区别；
- **导航**：补齐 TACAN 接收机等实际导航能力，保证航路、靶眼、航向与机场进离场程序一致；
- **机场调度**：多机起降排序、跑道占用、等待与复飞，支撑多单位场景；
- **空域划分**（新增）：管制区、扇区、警戒区、禁飞区与进出条件；空域约束要能被命令协议引用，并由程序校验。

验收：多机同时运行时，雷达情报、导航与机场调度不互相打架；进入受限空域会被程序拒绝或触发告警；空域定义有数据格式和测试。

### 5.4 AI 语言理解（資本の路灯）

现有基础：

- 云端指挥官模型 + 严格 JSON Schema + 字段级校验；
- 单/双机口令、机场、编队、雷达、武器等意图；
- 未接入能力返回 `capability_unavailable`，不假装执行。

本阶段目标：

- **多单位与持续意图**：把“Bravo 守住东侧，别追出防区”这类命令解析为可执行、可撤销、可条件触发的任务；
- **澄清与纠错**：对象、防区、时间、条件不明确时先澄清；人工改令使旧计划作废；
- **指挥语言**：与态势图、任务卡使用同一套任务模型，避免“说一套、执行一套”；
- **能力边界**：模型只提案，程序校验对象、参数、空域与物理可行性。

验收：一批真实口令（含多单位、持续意图、条件、撤销）通过模拟上游回归；错误对象/防区/越界指令被拒绝且有可读反馈。

### 5.5 对地攻击与地面防空（待定）

当前代码没有对地攻击执行器，也没有地面防空单位/威胁模型。先做两件事，不承诺时间表：

1. 定义能力边界与接口：目标类型、武器、交战规则、地面威胁对指挥决策的影响；
2. 确定负责人和优先级，再决定是接入现有 `attack_tasking`，还是作为新模块实现。

在实现前，界面与文档必须继续标记为“待接入/待定”，不得用模型输出冒充执行结果。

### 5.6 跨模块工程（全员）

- 命令协议、世界状态、事件与存档的版本化；
- 核心循环的自动化回归与可复现场景；
- Godot 移植清单：模块边界、可复用逻辑、需要重写的表现层；
- 文档与分工同步更新，避免“代码一套、文档一套”。

## 6. 里程碑（截至换引擎前）

## 8. 待定问题

- 玩家一次指挥的单位规模：4 架、8 架还是更多？规模直接决定交互与性能预算。
- 时间尺度：实时、可暂停实时，还是带时间压缩？影响“时机取舍”的表达。
- 对地攻击与地面防空的优先级、负责人和拟真深度。
- 单人还是多人；若多人，权威模拟与身份认证方案。
- Godot 技术选型：GDScript 还是 C#；仿真内核是移植为 GDScript/C#，还是保留独立逻辑层通过接口调用。
- PVE 关卡是手工设计、脚本化，还是提供编辑器。
- 现有 Web 原型在换引擎后的定位：只做验证台，还是保留为网页版。

## 10. 许可与合规风险

仓库根 `LICENSE` 为 MIT，但当前存在两处高风险冲突：

1. 回放解码工具与文档明确记录，帧格式、FM 布局和 ECS 结构“移植自” AGPL-3.0 的 wrpl-inspector，另参考了 AGPL-3.0 的 wrpl crate 与 wt_blk；
2. `terrain/airfields.json` 自身标注为 AGPL-3.0，来自 wrpl-acmi，与仓库的 MIT 声明冲突。

公开发布、商业化、提供网络服务或开始 Godot 移植前，先按 [LICENSE-RISKS.md](LICENSE-RISKS.md) 完成处置。换引擎不会消除 AGPL 义务；移植时要把许可边界一起搬过去。

此外，回放、载具名、飞行数据与地形均派生自《战争雷霆》本机文件，公开/商业发布前需评估版权、数据库权利与商标风险；WT-MAP-ANALYZE 与 War-Thunder-Datamine 的上游许可也需核实。
